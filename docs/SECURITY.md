# 安全策略

## 支持的版本

| 版本 | 支持状态 |
| --- | --- |
| 2.x | ✅ 接受安全报告与修复 |
| 1.x（旧 PHP 站点） | ❌ 不再维护（仅作迁移参考） |

## 报告漏洞

**请不要通过公开 Issue 报告安全问题。**

请使用 GitHub 仓库的 **Security → Report a vulnerability**（私密安全公告）提交，并尽量包含：

- 受影响的版本 / 提交
- 复现步骤或 PoC
- 影响范围（越权、XSS、SSRF、拒绝服务等）
- 你建议的修复方向（可选）

维护者会尽快确认，并在修复发布后与你协调公开披露。请勿在修复前公开细节。

## 安全模型

Lith Tools 假设部署者自行负责服务器、反向代理、TLS 与备份。应用层的主要防护：

| 风险 | 防护 |
| --- | --- |
| 密码泄露 | `scrypt` + 随机盐；`timingSafeEqual` 比对；不记录密码 |
| 会话劫持 | 256-bit 随机会话 ID；`HttpOnly` + `SameSite=Lax`；生产 `Secure`；改密/封禁清除会话 |
| CSRF | SameSite + 非 GET 请求的 `Origin`/Host 校验 |
| SQL 注入 | 全部参数化查询 |
| XSS | React 转义；Markdown 经 `DOMPurify` 消毒；不注入未消毒 HTML |
| 暴力破解 | 登录/注册/验证码/找回密码限流 |
| 越权 | 每个写接口校验资源归属与角色 |
| SSRF | 网络工具拒绝内网/保留地址，仅允许 80/443/8080/8443 |
| 密钥泄露 | SMTP / DeepSeek 仅服务端环境变量；前端不接触 |
| IP 封禁绕过 | 请求级拦截，API 与页面分别返回 403 |
| 依赖漏洞 | `npm audit`；Dependabot 自动更新 PR |

### 已知限制

- 限流为**单进程内存**实现，重启清零，多实例不共享。
- 未提供 MFA、账户锁定、密码历史、审计日志导出。
- SQLite 单文件适合单实例；多副本部署需要外部数据库或共享存储。
- 管理员拥有较高权限，生产环境请使用强密码并限制管理员数量。
- 网络工具的服务端探测仍属于对外请求能力，部署在敏感网络时建议在防火墙层限制出站。

## 部署加固清单

- [ ] 全站 HTTPS，保持 `COOKIE_SECURE=true`
- [ ] 修改默认管理员密码，必要时关闭公开注册（当前版本注册开放）
- [ ] 配置 `PUBLIC_ORIGIN` 与 `TRUST_PROXY`
- [ ] `.env` 权限 `600`，不进入版本库
- [ ] 反向代理限制请求体大小（建议 2 MB）
- [ ] 定期备份数据库并演练恢复
- [ ] 定期升级依赖与 Node.js
- [ ] 限制服务器出站，仅放行 SMTP 与所需第三方 API
- [ ] 监控 5xx、429 与异常登录

## 漏洞范围

以下情况通常**不视为**安全漏洞：

- 需要管理员权限才能执行的操作（管理员被视为可信）。
- 本地开发模式返回验证码 `devCode`（生产模式不返回）。
- 自托管部署未启用 HTTPS 导致的 Cookie 风险（属于部署问题）。
- 纯客户端工具处理的数据（不会离开用户设备）。
- 第三方上游服务（ipinfo、汇率、DeepSeek）自身的问题。

## 依赖与供应链

- 生产依赖数量刻意保持精简。
- CI 使用 `npm ci` 与锁文件，确保可复现构建。
- Dependabot 每周检查 npm 与 GitHub Actions 更新。
- 发布前运行 `npm audit --omit=dev` 并评估高危项。

## 安全更新流程

1. 私下确认问题与影响范围。
2. 在分支修复并补充回归测试（如适用）。
3. 发布补丁版本，更新 `CHANGELOG.md`。
4. 在安全公告中说明影响、修复版本与升级建议。
